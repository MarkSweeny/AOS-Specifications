1. Scope and controlled baseline

This annex is part of AOS-40's functional case definition. It fixes individually assessable variant identities, observable criteria, shared-view/endpoints, inherited local case coverage and residual preparation gates. A variant is not a new normative requirement or an execution result. Original parent expectations and local component cases remain necessary; passing one variant does not establish every parent obligation.

Baseline: AOS-00/Map v0.44; DEC-001–097; AOS-10v0.5/20v0.6/22v0.5/24v0.4/25v0.3/40v0.8; other components unchanged; Sharedv0.20/Corev0.6/Registerv0.19/Matrixv0.20; acceptance annexv0.2; reviewv0.3. FPv4/RPv6/GT, AOS-QS v0.1 and general controls retained; Phase2 use cases excluded.

The current functional planning population is 39 assembled cases with 110 independently assessable variants, including the retained Boundary, Resident and GI contrasts and the DEC-105 technical-control case. No live release or full-suite execution population has been selected. Every execution manifest must select exact component requirements, local cases, variant IDs, contracts/endpoints, methods and exclusions from this inventory and justify dependency effects. Scope cannot be reduced after a failed observation to manufacture a pass.

2. Common variant definition and result rules

Each variant below inherits its parent's method/assessor, original acceptance conditions and §12 evidence pack. Before execution, bind fixture values, source/profile/tool/contract/model revisions, permitted actors/destinations, clocks/units, failure injection, expected observations and comparison rubric in an approved run manifest. The fixture descriptions below define the required contrast; they do not supply production values. Observe actual upstream output, common record and downstream use/effect/duty state at each included boundary; a model narrative is not evidence.

For each variant retain exact linked requirement and local-case IDs; run/method/manifest; fixture and oracle; actual ordered steps, observations and prevented/allowed effects; assessor identity/capacity and rationale; timestamps/units; source/uncertainty; result, findings, accepted owner/cover/deadline and retest links; lawful lifecycle/access. A denied effect needs actual enforcement/sink evidence. Human usability/substantive judgement needs a competent approved rubric and representative human assessment. Data redaction must not falsely imply complete evidence; required unavailable evidence withholds dependent acceptance.

Variant statuses: planned, blocked, not-performed, running/interrupted, awaiting assessment, passed, failed, inconclusive or not-assessed. Each independently required assertion records its own observation and result; all required conjuncts must hold. An observed breach is failed, not inconclusive merely because other evidence is missing. Missing reliable observation after attempted execution is inconclusive; no execution is not-performed/blocked. A document walkthrough may assess proposed logic only, never pass implemented enforcement.

The parent may be marked passed for an exact assessed scope only when every required selected variant and original acceptance conjunct has accepted evidence. Failed required assertion means failed parent for that scope; blocked/unperformed/inconclusive/not-assessed required variants prevent a favourable complete result. Preserve the result vector when several states apply. No averaging away control failure or inventing pass percentages. A legitimately excluded variant must have recorded scope rationale, dependency assessment and owner before reliance; it gives no coverage contribution.

Quality acceptance uses approved task/population/rubric, repeated/contrast conditions, false and missed findings, material errors and variability. It never rescues a failed deterministic boundary. Model self-confidence is not calibrated assurance. An appointed qualified assessor judges actual evidence, not the producer's self-report. Operational and institutional approval remain separately empowered human acts.
